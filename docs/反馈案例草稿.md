# 处理反馈转案例草稿

更新日期：2026 年 11 月 23 日。

## 使用流程

1. 在问题助手保存处理反馈，或从「我的提问」打开已有问题。
2. 点击某份反馈的「整理为案例草稿」。这一步由用户主动触发，保存反馈本身不会调用模型或发布案例。
3. 核对原问题、实际反馈及材料。配置模型时生成结构化底稿；本地规则模式只预填问题及实际反馈，其他字段由人工填写。
4. 选择「新增案例」，或选择「修订已有案例」并指定同业务内已发布的目标。相似案例只提供候选，不自动决定合并。
5. 修订时对照原值和本地提案，可以逐字段采用原值，再手动合并本次反馈。点击「保存草稿」保留编辑，或「保存并提交人工确认」。
6. 问题处理人或知识维护人核对事实，知识维护人显式选择待验证、已验证或已失效后发布。选择已验证必须填写适用条件、处理步骤与实际验证记录。
7. 正式案例的「原始依据」显示已采用的反馈及相关问题截图；「版本记录」保留发布前后的案例。待确认页面可分别查看待处理、已发布的反馈草稿。

「已解决」是本次问题的处理进度，不自动设置案例有效性。仍未解决、不适用的反馈也可以形成待确认记录或修订建议，缺失事实必须保留为空。

## 版本、权限与恢复

- 同一份反馈最多一条草稿。重新生成时打开当前版本，保留已有人工修改。生成失败不会留下半成品或删除反馈，允许重试。
- 普通成员只能整理自己的反馈并编辑自己的草稿。同业务的问题处理人与知识维护人可以协作审核；只有知识维护人可以发布。授权同时覆盖问题、草稿、修订目标、原材料和附件。
- 整理规则与模型版本、耗时、最初生成内容、输入快照及每次保存和发布的操作主体均独立保留。正式案例读者只看到已采用的实际反馈，不获得私人分析记录和未采用的编辑历史。
- 修订提案在独立表中保存，提交审核不会改变线上案例。发布时同时检查草稿与目标案例版本，案例、历史版本、草稿去向及幂等结果在同一事务提交。
- 草稿或目标案例发生版本冲突时，页面保留本地正文并读取最新内容供对照。人工核对后采用新的基准版本，再保存提交；不会静默覆盖其他人的修改。
- 发布请求网络结果不明时，重试沿用原请求键。重复发布或不同请求并发发布都不会重复创建案例。
- 关闭存在未保存改动的草稿时显示提示；已保存的内容可以稍后继续处理。

## 接口与存储

以下路径均以 `/api` 为前缀，身份来自服务端 Cookie，会话、CSRF 和错误结构沿用现有接口约定。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /questions/{question_id}/feedback/{feedback_id}/draft` | 主动整理或打开该反馈已有草稿；要求 `Idempotency-Key` |
| `GET /feedback-drafts?business=...` | 列出当前业务下有权查看的草稿 |
| `GET /feedback-drafts/{draft_id}` | 读取完整草稿与修改历史 |
| `PUT /feedback-drafts/{draft_id}` | 携带草稿版本保存编辑或提交人工确认；修订携带目标版本 |
| `POST /feedback-drafts/{draft_id}/publish` | 维护人携带草稿版本与有效性发布；要求 `Idempotency-Key` |
| `GET /cases/{case_id}/feedback-evidence` | 案例读者读取已采用反馈的有限依据 |

`feedback_drafts` 以反馈编号建立唯一约束；草稿状态为 `draft`、`pending`、`published`。修订保留目标快照和版本，发布后记录正式案例编号及对应版本。原问题、分析、反馈和材料继续保持原有记录，不把整理文字伪装成微信原文。

新迁移为 `c4f7a92bd610`，依赖 `926a0d21805e`。既有部署更新代码后需执行 `npm run setup:api` 或在 `backend` 执行 `uv run alembic upgrade head`。升级仅新增草稿表，不回填已有业务数据。回退会删除草稿及整理审计，已经发布的案例与案例版本继续保留；有草稿数据后应先备份再考虑回退。

## 验收边界

自动测试使用隔离合成数据，覆盖新增与修订、普通成员与维护人权限、跨业务拒绝、无会话拒绝、输入和验证约束、重复请求、并发生成及发布、两类版本冲突、模型失败重试和等待期间撤权。前端交互测试覆盖冲突后保留输入、显式采用新版本以及发布重试复用请求键。

真实模型整理质量与正式部署仍需用实际供应商和业务样本验收。微信采集、截图识别、同一问题下的多次分析和任意两个已有案例的合并不属于本功能。
